## Резервирование и восстановление

Используйте Python установленного VAC, из активированного окружения. На Windows
можно заменить `python` на `.venv\Scripts\python.exe`, на Linux — `.venv/bin/python`.
Пути ниже замените своими; новый каталог создаётся автоматически.

```sh
python -m vac.storage.backup backup "данные/исследования.sqlite" "копии/2026-10-21.sqlite"
python -m vac.storage.backup verify "копии/2026-10-21.sqlite"
python -m vac.storage.backup restore "копии/2026-10-21.sqlite" "восстановление/исследования.sqlite"
```

Укажите восстановленный файл через меню **Архив** и откройте исследование,
сохранённую версию и отчёт. Для выдачи уже сохранённого DOCX через Python:

```python
from pathlib import Path
from vac.storage import Archive
with Archive("восстановление/исследования.sqlite") as archive:
    # Идентификатор отчёта получают через list_reports(interpretation_id).
    report = archive.open_report(report_id)
    Path("восстановленный отчёт.docx").write_bytes(report["payload"])
```

Команды возвращают количества записей по таблицам; ненулевой код возврата
означает неудачу. Существующий файл назначения никогда не перезаписывается.
`backup()` и `restore()` доступны также в `vac.storage.backup` как Python API.
Не используйте простое копирование открытого SQLite-файла: актуальные записи
могут находиться в WAL. Реализация использует SQLite Backup API и согласованный
снимок чтения. Незавершённая транзакция другого соединения в копию не попадает.

Временный файл создаётся рядом с назначением, проверяется и публикуется атомарной
жёсткой ссылкой без перезаписи; затем временное имя удаляется. Требуется локальная
файловая система с поддержкой hard links (например, NTFS/ext4); для FAT/exFAT
создайте копию на поддерживаемом диске и перенесите уже закрытый файл. Ошибка
публикации не создаёт готовую копию. Не заявляется гарантия против потери питания
или физического повреждения носителя. На время операции нужен свободный объём
для полного файла; назначения на сетевых дисках не проверены.

Храните датированные копии на другом физическом носителе; копируйте перед
обновлением приложения и после завершения рабочего исследования. Период,
число копий и рабочие объёмы пока не согласованы. Проверяйте восстановление
в отдельном каталоге, а не только наличие файла. Сохраняйте также установочный
пакет/исходный код соответствующей версии VAC: архив хранит версии и хеши кода,
но не полный комплект программы и зависимостей.

## Формат, проверки и миграции

Архив — один SQLite-файл, текущие миграции `001_initial.sql` и
`002_gui_snapshot.sql`. Схема этапа 9 не меняется. Метаданные и связи находятся
в таблицах; исходные LVM/TWF, доверенные legacy-вложения и DOCX — BLOB; числовые
массивы — NPY v1 без pickle с размером, dtype, shape и SHA-256. Включены входные
каналы/шум, оси, параметры, статистика, версии алгоритма и эталонов, автоматическая
и исправленная интерпретации, последовательность правок, интервалы и GUI-снимок.
Внешних файлов для открытия сохранённого исследования и отчёта не требуется.
Пользовательские TXT/PNG/DOCX вне БД включаются в копию только тогда, когда
соответствующий артефакт сохранён в архив; произвольный рабочий каталог не копируется.
Подробности модели и API: [этап 7](../stage-7/README.md),
[порядок работы GUI](../stage-8/README.md).

Проверка выполняет `integrity_check`, `foreign_key_check`, проверку SHA-256 каждого
исходника/отчёта/legacy-вложения и декодирование каждого числового массива с
проверкой размера и метаданных. Это проверка целостности, а не физической
корректности измерений. Она не исполняет pickle из legacy-вложений.
`backup` дополнительно проверяет совместимость и контрольные суммы миграций
на временной копии с откатом пробного обновления; версия схемы копии сохраняется.
`restore` выполняет обновление только копии и проверяет результат перед публикацией.
Самостоятельная команда `verify` проверяет целостность данных без миграции.

Перед обновлением VAC:

1. Закончите работу и создайте датированную резервную копию старым приложением.
2. Новым приложением выполните `restore` в новый путь; проверьте исследование,
   параметры, правки и отчёт. Исходный архив и резервную копию сохраните.
3. Откройте успешно восстановленный файл в GUI новой версии. Обычное открытие
   архива автоматически применяет известные миграции, поэтому сначала работайте
   с копией. Не открывайте единственный рабочий экземпляр для пробного обновления.
4. При неудаче продолжайте со старым приложением и неповреждённой копией старой
   схемы. Не удаляйте журнал миграций и не меняйте их хеши. Обратная миграция
   с сохранением данных не обещается; записи после резервирования нужно сохранять
   отдельно перед возвратом к старой копии.

Тест перехода 001 → 002 сохраняет существующую скважину. Ошибка следующего SQL
не публикует восстановленный файл, исходная копия остаётся доступной. Неизвестная
миграция или изменённая контрольная сумма приводят к отказу.

## Блокировки, повторный запуск и диагностика

Режим остаётся локальным однопользовательским; сетевой совместный доступ не
поддерживается. SQLite ожидает блокировку записи до 5 секунд. При `database is
locked` завершите операцию в другом экземпляре и повторите действие; не удаляйте
`-journal`, `-wal`, `-shm` вручную. Тест проверяет отказ второго писателя,
откат первого и успешную повторную запись. Отдельный процесс принудительно
завершается внутри записи; после открытия остаются только подтверждённые записи,
новая запись и проверка целостности успешны.

Для диагностического запуска:

```sh
# Linux
VAC_DIAGNOSTICS=1 python -m vac 2> vac-diagnostics.log
```

```powershell
# Windows PowerShell
$env:VAC_DIAGNOSTICS = "1"
python -m vac 2> vac-diagnostics.log
```

Для команд копирования добавьте `--verbose`. Библиотечные вызовы используют
стандартный `logging`, обработчики не создают. Сообщения VAC содержат этапы
импорта, расчёта/классификации, открытия/сохранения версии, миграции и копирования,
тип оборудования, количества, версии схемы, SQLite, хеши программы/алгоритма/
эталонов. Массивы, реквизиты скважины и содержимое файлов в эти сообщения не
передаются. Информационные сообщения по умолчанию выключены; сообщения сторонних
библиотек и уже существующие сообщения GUI имеют собственные правила вывода.

```sh

python -W ignore -m unittest discover -s tests/integration
python -W ignore tools/check_archive_reliability.py --output work/stage9-measurements.json
python tests/check_package.py
```

Итог: **11 unit- и 24 интеграционных теста пройдены**, включая 7 новых
проверок надёжности. Исходники и собранный wheel прошли проверку трёх
запусков из постороннего каталога; API и все три CLI-команды резервирования
проверены также из wheel без Qt.

Новые сценарии: полное восстановление всех записей в чистом каталоге и повторное
открытие, WAL, исключение незавершённой записи, повреждённый payload, неизвестная/
изменённая миграция, обновление копии и отказ SQL, блокировка и аварийный выход.
Полные GUI-циклы LVM/TWF восстанавливают сигналы, статистику, параметры,
автоматические/ручные таблицы, правки и интервалы без пересчёта; из восстановленной
версии создаётся Word, который повторно копируется и восстанавливается побайтно.
Эталоны фазы A и допуски не менялись, legacy TXT/PNG/DOCX/VAC остаются доступны.
Ядро проходит расчёт обоих примеров без Qt и подключения к БД.

До замера заданы инженерные бюджеты: импорт ≤ 2 с и открытие ≤ 1 с из этапа 6;
для полного расчёта без GUI — предварительная цель ≤ 5 с, чтобы отдельное действие
укладывалось в короткое ожидание специалиста. Это не согласованный SLA для
промышленных объёмов. Скрипт измеряет настоящий сервис импорта, восстановление
таблиц и полный headless-расчёт на двух поставляемых примерах, три повторения,
медиана; чтение тёплое, запись включает commit. Численные оптимизации не вводились.

## Ограничения и следующий шаг

`.vac` остаётся доверенным pickle-набором настроек и исправленной кривой;
не содержит исходные измерения, полные версии и историю. Импорт сохраняет
оригинальные байты и известные поля с пометкой неполноты; такой файл не заменяет
SQLite-копию. Чужой `.vac` может исполнять код; проверка резервной копии его не
распаковывает. Формулы, пороги, порядок загрузчиков и внешний вид формы сохранены.

Фаза B технически проверена на Linux на двух примерах; Windows, реальные
производственные объёмы, визуальная проверка GUI/Word, выбор носителя и графика
копий остаются открытыми. Следующий шаг — эксплуатационная приёмка архива;
этап 10 требует согласованной предметной выборки и критериев качества.
