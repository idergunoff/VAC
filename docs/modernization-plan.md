# Поэтапный план модернизации VAC

Дата: 20 октября 2026 года. Статус: начальный план, подготовленный по исходному коду.

## 1. Цель и порядок работ

VAC — настольное приложение для интерпретации виброакустической скважинной цементометрии и оценки качества цементажа. Модернизация выполняется последовательно:

1. Сделать текущую программу воспроизводимой и зафиксировать её поведение.
2. Разделить код на понятные модули, сохранив интерфейс, формулы, последовательность обработки и результаты.
3. Добавить базу данных для загрузки и долговременного хранения исходных измерений, параметров обработки, ручных корректировок и результатов.
4. После проверки совместимости развивать метод интерпретации на отдельной научно обоснованной основе.

На первом этапе не меняем методику, пороги классификации, форматы исходных измерений и внешний вид форм. Обнаруженные ошибки записываем отдельно. Если исправление необходимо для запуска, делаем его отдельным изменением с описанием влияния на результат.

Pandas сохраняется как инструмент обработки таблиц в памяти. База данных заменяет способ долговременного хранения и поиска данных; переносить каждое промежуточное вычисление в SQL не требуется.

### Уточнённые требования пользователя

- Основная платформа — Windows; Linux также используется и должен поддерживаться.
- Mini-версия сейчас не используется. Её исходники сохраняем как исторический материал; полноценное сопровождение отдельной mini-формы не входит в текущие критерии приёмки.
- На будущее предусмотреть работу основного интерфейса на небольшом экране без отдельной копии прикладной логики. Конкретные размеры экрана и масштабирование уточняются перед этой доработкой.
- На этапе разделения кода внешний вид основной формы сохраняется. Компоновка для небольших экранов выполняется отдельной задачей после стабилизации модульной версии.

## 2. Что установлено при первичном просмотре

Это статический обзор, а не подтверждение работоспособности всех сценариев.

| Объект | Наблюдение | Значение для плана |
| --- | --- | --- |
| `VAC_python.py` | 3017 строк; создание QApplication, глобальные таблицы, расчёты, графики, отчёты и привязки событий | Главный объект последовательного разделения |
| `VAC_python_mini.py` | 3017 строк; по сравнению с основной версией меняются импорт формы и разворачивание окна | Неиспользуемая копия; исключить дублирование прикладной логики |
| `VAC_dialog.py`, `VAC_dialog_mini.py` | Код форм, сгенерированный PyQt5 | Не переносить сюда прикладную логику; изменения через исходные `.ui` |
| `VAC_dialog.ui`, `VAC_dialog_mini.ui` | Две исходные формы интерфейса | Основная форма используется; mini сохранить как исторический материал |
| `standard.py` | Крупные массивы эталонных кривых | Сохранить значения и выяснить происхождение и единицы |
| `template.docx` | Шаблон Word-отчёта | Проверять таблицы, поля и изображения после переноса |
| `пример/новое оборудование` | Девять LVM-файлов во вложенных каталогах | Исходный набор для проверки нового оборудования |
| `пример/старое оборудование` | Тринадцать TWF-файлов | Исходный набор для проверки старого оборудования |

Ключевые связи в текущем коде:

- `open_dir`, `open_sig` загружают LVM; `open_dir_old`, `open_sig_old` — TWF. Чтение связано с изменением состояния виджетов и немедленными вычислениями.
- Для LVM используются столбцы глубины и сигнала, абсолютные значения, поиск максимумов, линейная интерполяция огибающей и скользящее среднее.
- Для TWF пропускаются 130 байт заголовка, читаются little-endian int32, используются коэффициенты 0.515 и 0.05839. Их физический смысл необходимо документировать, не исправляя предположениями.
- Назначение каналов и шума зависит от порядка чтения файлов. Для LVM есть обратная сортировка внутри каталогов; для TWF используется `os.listdir`. Переупорядочивание при рефакторинге может изменить результат.
- `all_signals`, `all_signals_old`, `all_stat`, `all_stat_old` и списки интервалов образуют разделяемое состояние. Часть других переменных возникает только после действий пользователя.
- `calc_to_int*`, `sum_signals*`, `calc_pdf*`, `k_damp_detect`, `calc_int_cement`, `cement_from_pdf*`, `cementogramma` смешивают вычисления и обращение к форме.
- `corr_sig`, `corr_sig_bottom`, `fix_corr`, `add_undefine` участвуют в ручной интерпретации. Её необходимо сохранять отдельно от автоматически полученных результатов.
- Программа пишет TXT/PNG/DOCX в текущий рабочий каталог. `save_cement` сохраняет параметры в `.vac` через `pickle`, `open_options` загружает их.
- Импорт основного файла создаёт окно и запускает цикл событий. Это мешает изолированному тестированию расчётов.

В корне репозитория при обзоре не обнаружены README, описание зависимостей и автоматические тесты. За пределами репозитория, в `/workspace/vac-setup`, есть установочный скрипт и smoke-проверка. Это вспомогательные материалы окружения: они не заменяют документацию и проверки внутри проекта; их успешное выполнение в этой работе не заявляется.

## 3. Общие правила выполнения

Каждый этап выполняется небольшими проверяемыми изменениями. Сначала описываем переносимую ответственность, затем переносим её, сравниваем поведение и обновляем документацию. Не совмещаем перенос функций с переписыванием формул, массовым переименованием столбцов или обновлением всех библиотек.

Для каждого изменения фиксируем: задачу, затронутые функции, способ проверки, результат сравнения и оставшиеся ограничения. Завершённый этап должен оставлять приложение запускаемым. Незавершённые части не отмечаем готовыми только по факту создания файлов.

При несовпадении результатов сначала выясняем причину: изменились входные данные, порядок каналов, настройки, зависимости или вычисления. Допуски нельзя расширять только ради прохождения проверки. Исправления старых ошибок получают отдельное описание и новые ожидаемые результаты.

2. Описать запуск основной версии на Windows и Linux, ожидаемый рабочий каталог и расположение ресурсов. Mini-версию отметить как неиспользуемую.
3. Собрать зависимости из импортов и проверить их в изолированном окружении. Начать с рабочего набора версий, затем отдельно решать вопрос обновления. Разделить пакеты приложения и инструменты разработки.
4. Проверить основную форму на Windows и Linux: графики, диалоги выбора файлов, шрифты, масштабирование и шаблон Word. Проверить пути с пробелами и кириллицей, разделители путей и регистр имён файлов. Отдельно различать headless smoke-проверку и ручную проверку реального GUI. Недоступную для проверки платформу явно отмечать как непроверенную.
5. Составить карту функций и глобальных переменных: кто создаёт, читает и меняет каждую таблицу, параметр и интервал. Выявить обязательный порядок действий.
6. Составить каталог выходных файлов и побочных эффектов: когда появляются TXT/PNG/DOCX/VAC, какие файлы перезаписываются.
7. Проверить полноту примеров и возможность их использования как тестовых данных. Не публиковать дополнительные промысловые данные без решения владельца.
8. Завести журнал известных проблем, не меняя расчёты в ходе инвентаризации.

**Результаты:** README с запуском; описание окружения; карта функций и состояния; список сценариев; журнал проблем; воспроизводимая установка зависимостей.

**Критерии завершения:** другой разработчик может установить зависимости и открыть основную версию по инструкции на Windows и Linux; каждый недоступный сценарий имеет описанную причину и следующий шаг. Одного факта появления окна недостаточно для признания приложения полностью рабочим.

**Результаты:** каталог сценариев, манифест эталонов, проверки сравнения и список известных несовпадений. Тестовые артефакты отделены от рабочих выходных файлов.

**Критерии завершения:** на одной конфигурации исходное приложение повторяет собственные результаты; оба типа оборудования охвачены; сценарии, которые нельзя воспроизвести, явно перечислены. Эталон означает совместимость со старой программой, а не доказательство физической корректности методики.

## 6. Этап 2. Каркас пакета и единая точка запуска

**Зависимость:** этап 1.

**Цель:** подготовить структуру без одновременного переноса всей логики.

3. Сделать основной запуск единым и исключить сопровождение двух копий прикладной логики. Неиспользуемые mini-файлы сохранить как исторический материал с явным описанием статуса. Не добавлять обязательный выбор формы. В дальнейшем поддерживать небольшие экраны средствами компоновки основного интерфейса.
4. Убрать зависимость поиска `template.docx` и эталонных данных от текущего каталога. Пути вывода пока сохранять совместимыми; изменение их пользовательского поведения вынести отдельно.
5. Зафиксировать правила генерации Python-файлов из `.ui` и версию генератора. Не править сгенерированные формы вручную.
6. Заменять wildcard-импорты явными по мере переноса; не смешивать это с массовым форматированием всего проекта.

**Результаты:** единый запуск и пакет, совместимые стартовые скрипты, инструкция по ресурсам и формам.

**Критерии завершения:** основная форма запускается на Windows и Linux с явной фиксацией фактически проверенных платформ; импорт вычислительного пакета не создаёт окно, не запускает event loop и не пишет файлы; эталонные сценарии сохраняют результат.

## 8. Этап 4. Разделение загрузки и вычислений

6. Выделить эталонные массивы из wildcard-импорта `standard.py` через явный интерфейс. Перенос в ресурс выполнять с проверкой длины, значений и порядка элементов.
7. После стабилизации отдельно улучшить сообщения об ошибках и пути вывода. Для изменения прежнего поведения описать новый сценарий и проверить отсутствие потери данных.

8. Зафиксировать отдельную будущую задачу для небольших экранов: определить минимальный размер окна и масштабирование Windows/Linux, проверить доступность всех действий и графиков; при необходимости использовать компоновки Qt, прокрутку и сворачиваемые панели. Не создавать отдельную копию вычислений или контроллеров. Реализацию этой задачи не смешивать с переносом кода.

**Результаты:** завершённая модульная версия без БД; таблица соответствия старых функций новым модулям; инструкции запуска и разработки.

**Критерии завершения фазы A:** основная форма работает с единым ядром на Windows и Linux; mini-версия обозначена как неиспользуемая; расчёты не импортируют Qt, отчёты или будущую БД; все эталонные сценарии проверены; старые настройки читаются в пределах зафиксированной совместимости; изменение методики отсутствует.

## 11. Этап 6. Требования к хранению и выбор базы данных

**Зависимость:** завершена фаза A.

**Цель:** выбрать хранение под реальные данные и режим использования.

**Действия:**

1. Измерить размер исходных наборов, число отсчётов и каналов, время загрузки, объём промежуточных результатов и ожидаемое количество скважин.
2. Уточнить режим: один пользователь на одном компьютере или несколько пользователей с общим архивом; обязательность автономной работы; целевые ОС; размещение резервных копий.
3. Описать необходимые запросы: поиск скважины, перечень исследований, повторное открытие, выбор обработки и получение данных по интервалу глубины.
4. Сравнить SQLite и PostgreSQL по измеренным требованиям. SQLite выбран для первой локальной реализации по результатам этапа 6; PostgreSQL остаётся вариантом для общего архива с конкурентной записью. См. [ADR-001](stage-6/adr-001-sqlite.md).
5. Отдельно сравнить хранение отсчётов строками, массивами/блоками и сочетание БД с внешними файлами. Бенчмарк должен включать чтение полного сигнала и интервала; не выбирать «одна строка на отсчёт» без оценки размера.
6. Если используются внешние файлы, определить переносимость путей, контрольные суммы, атомарность добавления и согласованное резервирование. Ссылка на файл без самого файла не обеспечивает сохранность исследования.
7. Зафиксировать решение отдельной записью: варианты, измерения, выбранный подход и ограничения. SQLAlchemy и Alembic — кандидаты для SQL-хранения и миграций, а не обязательная архитектура до выбора решения.

**Результаты:** требования к архиву, измерения объёмов, решение о СУБД и формате сигналов, черновая схема данных.

**Критерии завершения:** понятны автономность, многопользовательский режим, границы резервной копии и приемлемое время типовых операций; нет окончательного выбора только по привычке разработчика.

## 12. Этап 7. Схема данных и слой хранения

**Зависимость:** этап 6.

**Предварительные сущности:**

| Сущность | Что хранит |
| --- | --- |
| Скважина | Внутренний ID, номер/имя и согласованные реквизиты; один номер не считать глобально уникальным без проверки |
| Исследование | Связь со скважиной, дата при наличии, оборудование, описание и комплект измерений |
| Исходный файл | Оригинальное имя, формат, размер, контрольная сумма, исходное содержимое либо управляемое местоположение |
| Канал | Устойчивая идентичность, роль сигнала/шума, порядок, единицы и привязка к исходнику |
| Данные измерения | Шкала глубины и значения в выбранном формате; исходные и пересчитанные значения различимы |
| Запуск обработки | Снимок параметров, версия алгоритма и эталонов, версия программы, входной набор, время и статус |
| Результат | Производные сигналы, статистика и интервалы с явной системой классов |
| Ручная корректировка | Операция, порядок, параметры, связь с базовым результатом и при наличии автор |
| Отчёт | Связь с конкретной версией результата, реквизиты, версия шаблона и созданный файл |

**Действия:**

1. Уточнить единицы и допустимость отсутствующих значений. Не выводить физический смысл столбца из его технического имени.
2. Ввести первичные и внешние ключи, ограничения целостности, правила удаления и индексы под подтверждённые запросы.
3. Сохранить происхождение каждого результата: исходники → параметры → версия алгоритма/эталонов → ручные изменения → отчёт.
4. Описать репозитории через прикладные операции, например сохранить исследование, получить каналы, сохранить запуск, открыть результат. Не передавать ORM-объекты в расчёты и виджеты.
5. Реализовать транзакции и начальную миграцию схемы. Не заменять управляемые миграции только вызовом создания таблиц.
6. Определить повторный импорт: совпадение содержимого и совпадение имени различать; одинаковый файл в разных контекстах не удалять молча.
7. Защитить исходные измерения от перезаписи результатом обработки. Повторная обработка создаёт новую версию результата.

**Проверки:** создание пустой БД, применение миграции, сохранение и повторное чтение, целостность связей, точность чисел и глубины, откат транзакции при ошибке, работа с кириллицей.

**Критерии завершения:** сохранённое исследование восстанавливается без потери данных; неуспешная запись не оставляет «готовое» неполное исследование; версии обработки различимы и воспроизводимы.

## 13. Этап 8. Импорт существующих данных и подключение GUI

**Зависимость:** этап 7.

**Цель:** добавить архив, сохранив текущие способы работы с измерениями.

**Действия:**

1. Построить импорт LVM/TWF через уже выделенные загрузчики. Сначала чтение и проверка, затем сохранение согласованного комплекта в транзакции.
2. Сохранить оригиналы и фактическое соответствие каналов, включая шум. Техническую сортировку не подменять новым предметным правилом без решения специалиста.
3. Разработать отчёт импорта: принятые файлы, пропуски, дубликаты, ошибки, назначение каналов. Повторный запуск после сбоя должен иметь понятный результат.
4. Для `.vac` реализовать совместимый перенос только реально содержащихся полей. Если исходников или параметров недостаточно, отмечать неполноту, а не придумывать значения.
5. Добавить минимальный сценарий GUI: выбрать скважину/исследование, загрузить комплект, открыть сохранённый набор, выполнить обработку, сохранить версию и повторно открыть её.
6. При открытии результата различать восстановление сохранённой версии и новый расчёт текущей версией алгоритма. Новый запуск не перезаписывает прежнюю интерпретацию.
7. Сохранить существующие экспорт и Word-отчёт. Использовать данные выбранной версии результата и её ручные корректировки.
8. На переходный период сохранить прямую загрузку файлов. После проверки описать, что становится основным способом хранения, а что остаётся экспортом или совместимостью.

**Проверки:** импорт обоих комплектов из `пример`; повторный импорт; имена на кириллице; сбой в середине операции; закрытие приложения и открытие исследования; совпадение расчётов до и после сохранения; восстановление ручных изменений и отчёта.

**Критерии завершения:** полный цикл «импорт → обработка → корректировка → сохранение → перезапуск → открытие → отчёт» работает для обоих типов оборудования и сохраняет численные результаты фазы A.

## 14. Этап 9. Надёжность хранения и завершение перехода

**Зависимость:** этап 8.

**Действия:**

1. Реализовать и документировать резервное копирование БД вместе с исходниками и внешними артефактами, если они хранятся отдельно.
2. Проверить восстановление на чистом каталоге/экземпляре, включая каналы, параметры, ручные изменения и отчёт. Наличие файла копии само по себе не считается проверкой.
3. Проверить обновление схемы на копии существующего архива; описать восстановление из копии при неудаче. Откат схемы с потерей данных не обещать автоматически.
4. Проверить конкурентные операции, только если выбран многопользовательский режим; для локального режима проверить блокировки и повторный запуск.
5. Измерить время импорта, открытия и обработки представительного набора. Критерии скорости установить до оптимизаций на основании рабочего сценария.
6. Добавить диагностические сообщения об этапах обработки и версиях без вывода полных промысловых массивов в журналы.
7. Обновить пользовательскую инструкцию, описание формата архива, миграций и ограничений legacy `.vac`.

**Критерии завершения фазы B:** данные переживают перезапуск и проверенное восстановление; миграции воспроизводимы; старый экспорт работает; вычислительное ядро по-прежнему запускается без БД и GUI.

## 15. Этап 10. Развитие метода интерпретации

**Зависимость:** завершена фаза B; есть согласованный набор данных и критерии оценки.

**Цель:** улучшать качество интерпретации с измеримым эффектом, сохраняя воспроизводимость прежних результатов.

**Действия:**

1. Совместно описать физические предпосылки текущего метода, происхождение эталонов, коэффициентов и порогов, ограничения по оборудованию и условиям скважины.
2. Собрать экспертную разметку интервалов: качественный цемент, частичный цемент, отсутствие цемента и неопределённость. Уточнить неоднозначные границы и различия между экспертами.
3. Подготовить независимую оценочную выборку. Разделять данные по скважинам/исследованиям, чтобы соседние отсчёты одного сигнала не попадали одновременно в обучение и оценку.
4. Оценить действующий метод как базовую версию. Выбрать метрики для классов и интервалов: ошибки по классам, совпадение интервалов, ошибка границ и доля неопределённых результатов. Конкретные критерии согласовать с предметным специалистом.
5. Исследовать по одной гипотезе: предобработка, устойчивость к шуму, нормирование, объединение каналов, пороги, оценка неопределённости. Не объединять несколько изменений без возможности оценить вклад каждого.
6. Для эксперимента сохранять данные, параметры, версию кода, эталоны и результаты. Сопоставлять качество на независимых данных, а не только визуальный вид удачного примера.
7. Хранить старую и новую версии алгоритма рядом. Применение новой версии создаёт новый запуск; старый отчёт остаётся связан с прежним результатом.
8. Перед использованием новой методики в рабочем процессе провести предметную проверку спорных интервалов и документировать ограничения.

**Критерии завершения отдельного улучшения:** понятна гипотеза, измерен эффект относительно базовой версии, оценена устойчивость на независимых исследованиях и сохранена возможность воспроизвести прежнюю интерпретацию. Машинное обучение не является обязательной целью этого этапа.
