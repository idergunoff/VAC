## Принятые требования

SQLite выбран для первой реализации по предпочтению пользователя и измерениям,
см. [решение ADR-001](adr-001-sqlite.md) и [черновую схему](schema.md).
На этапе 6 добавлены только документация, эксперимент и его результаты:
приложение пока не создаёт БД. Репозитории и управляемые миграции — этап 7;
импорт архива и подключение GUI — этап 8; восстановление копий — этап 9.

| Требование | Основание и границы |
| --- | --- |
| Автономная работа | Рабочее предположение: архив полностью доступен без сети и сервера |
| Один пользователь, один компьютер | Рабочее предположение; одновременная запись нескольких специалистов не включена |
| ОС | Windows — основная, Linux поддерживается; измерения выполнены только на Linux |
| Размещение | Один локальный SQLite-файл в доступном для записи каталоге пользователя; путь задаётся явно, не зависит от текущего рабочего каталога |
| Объём | Реальное количество скважин и исследований неизвестно; два примера не являются прогнозом промышленного архива |
| Резервирование | Настраиваемое место копий, желательно другой физический носитель; конкретное место, период и срок хранения пока не заданы |
| Переносимость | Копия архива содержит оригиналы, массивы, параметры, результаты, исправления, реквизиты и отчёты; внешние абсолютные пути не нужны для открытия |
| Совместимость | Исходники неизменяемы; новая обработка создаёт новую версию, сохранённая интерпретация не пересчитывается при открытии |
| Воспроизводимость | Фиксировать порядок и роли каналов, версию загрузчика, параметры, код, эталоны и последовательность ручных изменений |

Для первоначальной проверки принимаем инженерные цели на поставляемых примерах:
импорт с записью до 2 с, открытие полного набора до 1 с, чтение интервала до
200 мс. Это бюджет операций хранения, без построения графиков и полного
расчёта. Он выбран для интерактивного настольного сценария; это не измеренный
SLA на Windows или больших архивах. Полный импорт приложения будет проверяться
после этапа 8. При появлении рабочих объёмов повторить измерения до оптимизации.

## Запросы и операции

1. Найти скважину по имени/номеру и уточняющим реквизитам; номер не уникален
   глобально. Показать исследования выбранной скважины с оборудованием, датой
   (может отсутствовать), описанием и состоянием комплекта.
2. Открыть исследование: оригиналы и их хеши, точный порядок каналов/шума,
   технические шкалы, версии загрузки; загрузить массивы в pandas/NumPy.
3. Показать версии обработки и отдельно открыть сохранённую версию с параметрами,
   результатами, ручными изменениями и отчётами. Новый расчёт — отдельная операция.
4. Прочитать полный канал или включительный интервал `[начало, конец]` по его
   шкале. Единицы неизвестных осей не домысливать; физическую глубину скважины
   и техническую ось сигнала не объединять автоматически.
5. Добавить согласованный комплект одной транзакцией. Повторное имя с другим
   содержимым и одинаковое содержимое в другом исследовании различать; хеш
   используется для обнаружения повторов, а не молчаливого удаления контекста.
6. Сохранить новую обработку и её исправления, затем отчёт, связанный с точной
   версией. Ошибка не оставляет неполную версию со статусом «готово».

## Измерения

Повторение из корня репозитория в окружении приложения:

```sh
python tools/benchmark_storage.py --output work/stage6-measurements.json
```

Сохранённый прогон: [measurements.json](measurements.json). Python 3.12.14,
NumPy 1.26.4, SQLite 3.53.1, Linux. Использованы текущие `vac.io.lvm` и
`vac.io.twf`, без Qt и изменения вычислений. Загрузка включает предобработку
загрузчика: огибающие LVM, интерполяцию/нормирование TWF; это не время полного
расчёта. Медиана трёх загрузок и семи чтений с прогретым файловым кешем;
одна запись с commit на каждый вариант. Холодный диск и конкуренция не измерены.

| --- | ---: | ---: |

| Размер оригиналов, байт | 973 972 | 21 814 |
| Исходных отсчётов на файл | 3425 | 387 |

Последняя строка включает данные графиков и повторяющиеся массивы, исключает
Python-объекты, строковую статистику и JSON. Это не пик RSS и не обязательный
размер версии в БД. Не следует хранить все 12 регрессионных снимков как один
рабочий результат. Для TWF оригинальный int32 и пересчитанный float64 — разные
данные; маленький исходник не означает маленький результат.

В эксперименте каждый канал представлен парами float64 «ось, значение»,
без сжатия; ось для сравнения дублируется. Метаданные эксперимента одинаковы;
оригинальные файлы/отчёты в размеры ниже не входят. Внешний вариант включает
и SQLite-каталог, и NPY-файлы. В промышленной схеме общая шкала хранится отдельно.

Все четыре варианта прошли точное сравнение полного набора и интервала,
`PRAGMA integrity_check`; выбор интервала из BLOB/NPY включает десериализацию
и фильтрацию в NumPy. Блоки выбираются SQL по пересечению границ, затем фильтруются
точно. Интервальные запросы строк используют индекс `(channel, depth)`.
Упорядочение всегда по номеру отсчёта, без изменения порядка каналов.

Повторный прогон подтвердил контрольные суммы файлов, порядок каналов, число
отсчётов, числовые объёмы и размеры всех восьми вариантов архива; точное чтение
прошло повторно. Существующие 11 unit-тестов ядра/состояния прошли; были прежние
предупреждения pandas о фрагментации и сравнении None/NaN. `git diff --check`
пройден. Сводка проверок: [validation.json](validation.json).

## Ограничения и следующий шаг

На этих примерах целые BLOB дают достаточно быстрый доступ и примерно в 3.7–3.8
раза меньше места, чем строки с индексом. Разница с внешними файлами не
обосновывает усложнение транзакций и копирования. На огромных каналах блоки могут
оказаться полезнее; текущие размеры не требуют их вводить сразу.

Прогноз количества скважин отсутствует. Для планирования использовать формулу:
сумма оригиналов + выбранные шкалы/каналы + сумма сохранённых версий + отчёты +
индексы/свободные страницы SQLite; резервные копии считаются отдельно. Например,
1000 копий приведённых измерительных массивов — сценарий расчёта ёмкости, а не
подтверждённая потребность. Большие наборы и Windows требуют отдельных прогонов.

Формулы, UI, эталоны и загрузчики не менялись. Полная приёмка Windows/реального
GUI из фазы A остаётся открытой независимо от выбора СУБД. Следующий шаг —
этап 7: миграции и репозитории по черновой схеме с проверками точности, транзакций,
кириллицы и неизменяемости исходников. Эксплуатационные предположения пересмотреть,
если потребуется общий архив или будет известен фактический объём.
