# ADR-001: локальный SQLite-архив с массивами в BLOB

Статус: принято для первой локальной реализации; дата 20 октября 2026.
Основание: предпочтение пользователя «скорее всего нам вполне хватит sqlite»,
текущая настольная архитектура и [измерения](README.md#измерения).
Однопользовательский режим — рабочее предположение, не подтверждённый масштаб.

## Сравнение СУБД

| Критерий | SQLite | PostgreSQL |
| --- | --- | --- |
| Автономное настольное приложение | Встроен, отдельный сервер не нужен | Требует локальный или доступный удалённый сервер |
| Поставка Windows/Linux | `sqlite3` стандартной библиотеки Python | Драйвер, установка, учётные записи и сопровождение сервера |
| Одновременная запись | Один writer, нужны короткие транзакции и обработка busy | Подходит для нескольких конкурентных writers |
| Объёмы примеров | Чтение комплектов менее 2 мс для BLOB | Не измерялся: общий сервер сейчас не обоснован |
| Целостность и версии | Транзакции, FK с явным включением, управляемые миграции | Транзакции, FK, управляемые миграции |
| Резервирование | SQLite backup API, единый архив | Серверное резервирование и отдельное обслуживание |

Выбран SQLite. PostgreSQL не объявляется медленнее и не исключается навсегда:
серверный бенчмарк не проводился, поскольку нет подтверждённого общего архива.
Рассмотреть PostgreSQL при общей БД нескольких специалистов с конкурентной
записью, централизованными правами/аудитом или неудовлетворительных измерениях
рабочего масштаба. Не размещать живой SQLite-файл на сетевой папке или в каталоге
синхронизации; туда можно отправлять завершённые согласованные копии.

## Формат данных

Метаданные, версии, интервалы и связи — обычные таблицы. Оригинальные LVM/TWF,
отчёты и массивы — внутри того же SQLite-файла, BLOB. Измеренные выигрыши внешних
файлов малы, а внешнее размещение добавляет разрыв транзакции БД/файловой системы,
управление относительными путями и согласованное копирование каталога.

Числовые массивы: NPY без pickle, один массив на BLOB, явные dtype/shape,
версия кодека и SHA-256 байтов. Для текущих расчётных float64 сохранять float64
без округления и потерь; исходные int32 TWF и оригинальный заголовок сохраняются
в оригинале. Не превращать NaN в NULL в массивах; сохранять NaN/Inf и форму.
При чтении использовать `allow_pickle=False`, разрешённые числовые dtype,
проверки формы, размера и контрольной суммы. Object-массивы запрещены.
Шкала хранится самостоятельно и ссылается из каналов с той же шкалой; не выводить
её заново из округлённого шага. Разные шкалы и длины не объединять искусственно.

Полный сигнал читается одним BLOB; интервал выбирается NumPy-маской включительно
с обеих сторон. Для будущих больших каналов допустим переход к блокам с
индексированными границами и номерами отсчётов через новую миграцию/кодек.
1024 — параметр эксперимента, не утверждённый производственный размер блока.

Строки на каждый отсчёт отвергнуты для первой реализации: больше места и накладных
расходов при основном сценарии чтения полного сигнала. Для небольших таблиц
статистики, ручных операций и интервалов реляционная форма остаётся удобной.

## Реализация в следующих этапах

Использовать стандартный `sqlite3`, явные прикладные репозитории, транзакции и
нумерованные SQL-миграции с журналом версии/контрольных сумм. SQLAlchemy/Alembic
не требуются для одной встроенной СУБД. Если появится второй backend, пересмотреть
адаптер; виджеты и вычислительное ядро не получают соединение или ORM-объекты.

На каждом соединении включать `foreign_keys`, задавать ограниченный busy timeout
(первоначально 5 с), сообщать о блокировке без частичного сохранения. Начать с
обычного rollback journal и коротких транзакций; WAL вводить по измеренной
необходимости, а не как условие автономной работы. Не снижать durability ради
бенчмарка. Ограничить размер входов до выделения памяти, проверить реальную
версию SQLite на Windows/Linux при поставке.

Граница резервной копии — весь согласованный архив через `Connection.backup()`
в новый файл, затем проверка целостности и пробное открытие на этапе 9. Не
копировать живой файл обычным файловым копированием. Копия должна включать
оригиналы и артефакты: внешние пути используются только как сведения происхождения.
Приложение и код/эталоны соответствующей версии сохраняются отдельно в поставках;
один идентификатор версии не гарантирует доступность старого алгоритма.

Риски: рост архива с версиями и DOCX, один writer, чтение полного большого BLOB
для маленького интервала. Пока нет данных, обосновывающих более сложное хранение.
Резервирование, блокировки, сбои и миграции описаны как требования; на этапе 6
промышленный слой хранения ещё не реализован и не считается проверенным.
